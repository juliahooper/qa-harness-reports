## Suggested Skill Doc Improvements

- **[jentic-cli-skill]** In the "Check what you can do" section (step 2), add a fourth denial type after `ambiguous_toolkit`: **`permission_rule_denial` (403)** — you're bound to a toolkit for this API, but a permission rule on that toolkit blocks this specific operation. The directive explains the denial reason. Unlike `no_toolkit_binding`, filing another access request will not help—permission rules are configured by the toolkit owner. If you believe you should have access, share the operation details and denial reason with your operator to review the toolkit's permission rules.
- **[jentic-cli-skill]** In the "Quick Reference" section, add after the `jentic access whoami` line: Note that `whoami` shows which toolkits you're bound to, but does not show the permission rules configured on those toolkits. If an `execute` is denied by a permission rule, there is currently no CLI command to inspect those rules—share the denial with your operator.
- **[find-credential]** Add a note after "its authentication requirements": Note that `jentic inspect` may show `"auth": null` even when the upstream API requires authentication—the broker handles credential injection transparently when you execute through a toolkit. The `auth` field reflects what's declared in the OpenAPI spec, which may be incomplete.
- **[make-proxied-request]** Add before "Before moving on": If `execute` fails with "denied by a toolkit permission rule" (exit code 2), this means the toolkit you're bound to has rules that block this specific operation. This is distinct from having no toolkit binding at all. There is no self-service CLI path to view or modify permission rules—document the denial details and consult your operator about the toolkit's configuration.
