## Suggested Skill Doc Improvements

- **[jentic-cli-skill] Step 3 (Find an operation)**: Add explicit note that for a **local test environment**, the test API may already be in the registry and searchable without import. Clarify the expected command sequence when starting fresh vs. when APIs are pre-populated.
- **[jentic-cli-skill] Step 3 (Find an operation)**: Expand the `jentic apis operations` example to show the exact format of the vendor/name/version argument (e.g., `jentic apis operations vendor-name/api-name/1.0.0`) and note that this is the most direct way to list operations for a known API without searching.
- **[jentic-cli-skill] Step 4 (Inspect the operation's contract)**: Clarify that `inspect` accepts **three distinct formats**: (1) registry `operation_id` from `search`/`apis operations`, (2) `METHOD URL` pair (with space, not colon), and (3) spec `operationId` from `catalog show` (fallback only). Show an example of each and note which is preferred.
- **[jentic-cli-skill] Step 5 (Execute through the broker)**: Explicitly state that the target URL in `execute` must be the **full upstream URL** (the actual API endpoint), not a broker path or relative path. Add a note that on local installs, the broker host defaults to an unreachable cloud address and must be overridden via config or flags.
- **[find-credential] Goal doc**: Add a prerequisite note: "Before starting, confirm your identity with `jentic profile list` and ensure an active profile with a valid token exists. If not, ask your operator to run `jentic bootstrap`."
- **[add-to-toolkit] Goal doc**: Clarify that `--wait` blocks until human approval and exits with code 0 (approved) or 2 (denied). Note that if denied with "No toolkit serves API …", the toolkit must be created and a credential bound by an operator before re-filing.
- **[make-proxied-request] Goal doc**: Add a note that the `execute` command target should be the full upstream API URL (e.g., `GET http://test-api:8080/get`), not a registry reference or broker path.
