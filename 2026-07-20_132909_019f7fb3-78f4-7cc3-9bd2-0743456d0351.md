## Journey

The agent successfully completed all three onboarding goals: discovering the test API in the registry, requesting and receiving access approval to a toolkit, and making a proxied request through the broker. The agent demonstrated good problem-solving by exploring multiple endpoints, examining OpenAPI specs, and iterating on the broker URL format until finding the correct pattern (full upstream URL including protocol/host).

## Key Friction Points

- **Toolkit/credential visibility gap**: After access request approval, the agent expected to see the toolkit or credentials in `/toolkits` or `/credentials` endpoints but found empty lists, causing confusion about whether the approval actually worked
- **Broker URL format discovery**: Required 5+ failed attempts (tried `/get`, with `Jentic-Api` header, `jentic-test.test-api` format, `test-api` format) before discovering the correct format requires the full upstream URL including `http://`
- **Resource discovery for access requests**: Agent struggled to understand what `resource_id` or `resource_reference` to use in the access request, noting "no obvious way to discover what resources exist"
- **Security scheme information**: The `/security_schemes` endpoint returned empty, and the OpenAPI spec didn't show the X-API-Key requirement mentioned in the task context

## Unlogged Insights

- Agent attempted to use the `/catalog` endpoint thinking it might list available toolkits/credentials, but discovered it only shows external APIs from a public repository
- Agent examined the `binding_id` from the access request response and looked for binding endpoints to understand what was created, but found no explicit binding API
- Agent inferred that the binding grants broker authorization rather than direct credential visibility, which wasn't explicitly documented

## Suggested Skill Doc Improvements

- **[find-credential]** Add guidance that security requirements may not be visible in `/security_schemes` or OpenAPI specs initially, and that authentication details become available after access approval
- **[add-to-toolkit]** Clarify that toolkits/credentials may not appear in listing endpoints (`/toolkits`, `/credentials`) even after approval, and explain that approval creates a binding that authorizes broker access rather than exposing credentials directly
- **[add-to-toolkit]** Add context about discovering available resources for access requests — explain whether agents should use search, inspect specific APIs, or expect resources to be pre-communicated
- **[make-proxied-request]** Document the broker URL format explicitly: requests should use the pattern `/{full_upstream_url}` where the upstream URL includes protocol and host (e.g., `/http://test-api:8080/get`), and note this can be found in the API's registered `url` field via search/inspect
- **[make-proxied-request]** Mention that response headers (`jentic-execution-id`, `jentic-toolkit-id`, `jentic-operation`) provide useful metadata for verifying the request was properly brokered
