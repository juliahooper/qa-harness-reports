## Key Friction Points

- **API reference format confusion**: Agent tried multiple formats before finding the correct one—`jentic apis inspect` rejected "jentic-test/test-api" (needed version), then "jentic-test/test-api/1.0.0 GET /get" failed. - **Command vs. subcommand ambiguity**: Agent initially tried `jentic apis inspect` with an API reference, then had to discover that `jentic inspect` (without the `apis` subcommand) was the correct command for operation inspection.
- **Auth metadata interpretation**: The `jentic inspect` output showed `"auth":null` despite instructions stating the API requires an `X-API-Key` header, causing momentary confusion about whether authentication was handled separately through toolkits or missing from the spec.

## Suggested Skill Doc Improvements

- **[find-credential]** Add a note clarifying the distinction between `jentic apis show` (for API-level metadata) and `jentic inspect` (for operation-level details), and specify that `inspect` accepts operationId from the API's operations list
- **[jentic-cli-skill]** In section 4 ("Inspect the operation's contract"), add an example showing the progression: `jentic apis operations <vendor/name/version>` → extract `operation_id` → `jentic inspect <operation_id>`, to clarify the relationship between these commands
- **[jentic-cli-skill]** In the Quick Reference, clarify that `jentic inspect` is a top-level command (not `jentic apis inspect`) and explicitly state it accepts the `operation_id` field from `jentic apis operations` output
- **[jentic-cli-skill]** Add a brief note in section 4 explaining that `"auth":null` in inspect output means authentication is handled by the broker/toolkit layer, not that the API is unauthenticated—this would reduce confusion when OpenAPI specs don't declare security schemes
