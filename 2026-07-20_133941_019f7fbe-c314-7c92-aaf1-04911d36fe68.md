## Journey

The agent successfully completed all three onboarding goals in sequence: discovered the test API using `jentic apis list` and `jentic inspect`, requested and received auto-approved toolkit access via `jentic access request --toolkit`, and executed a successful proxied GET request through the broker. The agent demonstrated good problem-solving when encountering command syntax errors and adapted by using alternative approaches (e.g., querying the API directly with curl when CLI commands weren't available).

## Key Friction Points

- **No CLI command to list available toolkits** — Agent attempted multiple approaches (`jentic toolkits list`, checking admin commands, exploring endpoints) before resorting to direct API calls with curl to discover that no toolkits existed yet. This was the primary UX gap noted.
- **Command syntax trial-and-error** — Agent encountered multiple syntax errors: invalid API reference format (missing version), incorrect argument count for `jentic inspect`, and unknown `jentic endpoints list` command. Required several retries to find correct formats.
- **Confusion about toolkit creation vs. access** — Agent initially wondered whether toolkits needed to be created manually or if the platform expected access requests first, showing uncertainty about the expected flow.
- **Token refresh uncertainty** — After receiving toolkit binding, agent noticed token_scopes hadn't updated and proactively refreshed the token, but wasn't certain this step was necessary.

## Suggested Skill Doc Improvements

- **[jentic-cli-skill]** Add explicit guidance that on a fresh deployment, no toolkits exist until access is requested — clarify that `jentic access request --toolkit` will trigger toolkit creation (via auto-approval in test environments) rather than requiring pre-existing toolkits
- **[jentic-cli-skill]** Document that there is no `jentic toolkits list` command; agents should use `jentic access whoami` to see their own bindings, and clarify that discovering *available* toolkits before requesting access is not a supported workflow
- **[add-to-toolkit]** Add a note that the access request may create the toolkit if it doesn't exist (in auto-approval scenarios), so agents shouldn't expect to discover existing toolkits first
- **[jentic-cli-skill]** In the "Quick Reference" section, add the expected format for API references (`vendor/name/version`) alongside commands that require them to reduce syntax trial-and-error
- **[jentic-cli-skill]** Clarify whether `jentic access refresh` is required after receiving a new toolkit binding, or if it only applies to scope grants (the current text only mentions refreshing after scope grants)
