Journey

The agent successfully completed all three onboarding goals: discovering the test API in the registry, requesting and receiving toolkit access, and executing a proxied GET request through the broker. The workflow was linear and the core functionality worked end-to-end, though the agent encountered several UX friction points requiring trial-and-error to resolve.

Key Friction Points

  • Operation ID discoverability: jentic apis operations output doesn't display operation IDs, but jentic apis inspect requires them. The agent had to infer the relationship from help text rather than having it explicitly documented.
  • Execute format ambiguity: The agent tried broker-relative path format (GET:/get) first, received a 404, then had to backtrack and try the full URL format (GET:http://test-api:8080/get). The skill doc mentions three targeting methods but doesn't clarify when each applies or what error to expect from wrong formats.
  • Security scheme gap: The OpenAPI spec didn't include security scheme details (e.g., X-API-Key header requirement). The agent had to infer this information was stored in toolkit/credential setup rather than the API spec itself.
  • Toolkit discovery: The agent had to already know the toolkit vendor/name to request it. No CLI command exists to browse available toolkits, limiting discoverability for new users.
  • Command name typo recovery: The agent tried jentic api instead of jentic apis and received a helpful error message, but this represents a minor UX gap.

Unlogged Insights

  • The agent appreciated the --wait flag for access requests, noting it made the approval flow "seamless" and transparent (< 5 seconds).
  • The agent explicitly noted that credentials were never exposed to the agent — the CLI never showed API keys and the broker handled injection transparently.
  • The agent recognized that the three-command structure (apis, access, execute) is "well-organized" with "good help text and error messages," suggesting the overall CLI design is sound despite specific friction points.

Suggested Skill Doc Improvements

  • [jentic-cli-skill] Clarify operation ID retrieval: In the "Find an operation" section (step 3), explicitly state that jentic apis operations <vendor/name/version> output includes operation IDs in a specific column/field, and show an example of passing that ID to inspect. Currently the relationship between the list output and the inspect requirement is implicit.
  • [jentic-cli-skill] Document execute format error handling: In step 5 ("Execute through the broker"), add a note explaining that broker-relative paths (e.g., GET:/get) will return a 404 "Operation not found" error, and clarify that the full upstream URL format (scheme + host + path) is required. Show both a failed and successful example.
  • [jentic-cli-skill] Add toolkit discovery guidance: In step 2 ("Check what you can do"), add a sentence noting that if you need to request access to a toolkit but don't know its vendor/name, you can ask your operator or check internal documentation — there is no CLI command to list available toolkits. This sets expectations upfront.
  • [find-credential] Note on security scheme documentation: Add a note that OpenAPI specs may not include all authentication details (e.g., required headers). If the spec is incomplete, check the toolkit or credential setup documentation for full auth requirements.
