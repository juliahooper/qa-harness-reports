## Key Friction Points

- **Command naming inconsistency**: Typed `jentic api` instead of `jentic apis`, triggering a helpful error but revealing inconsistency with other commands like `jentic access` (singular)
- **Operation ID discovery gap**: The `jentic apis operations` command shows method/path/description but not the `operation_id` needed for `inspect`, forcing the agent to guess, download the full spec, or use alternative approaches
- **Manual token refresh required**: After access approval (even with `--wait`), had to manually run `jentic access refresh` to activate the toolkit binding—this step wasn't documented or prompted
- **Multi-step discovery process**: Required chaining multiple commands (`apis list` → `apis show` → `apis spec` or `inspect`) to understand the full API contract
- **Authentication requirements hidden**: API authentication/security schemes not exposed during the discovery flow

## Suggested Skill Doc Improvements

- **[jentic-cli-skill]** Add explicit note in section 2 ("Check what you can do") that after an approved access request with `--wait`, you must run `jentic access refresh` before the toolkit binding becomes active in your token
- **[jentic-cli-skill]** In the Quick Reference, clarify that `jentic apis operations` output does not include the `operation_id` field—recommend using `jentic search` results or the `_links.inspect` URL to obtain operation identifiers
- **[find-credential]** Add guidance that authentication requirements are not directly exposed via CLI discovery commands; note that security schemes are embedded in the OpenAPI spec but not surfaced in `inspect` output
